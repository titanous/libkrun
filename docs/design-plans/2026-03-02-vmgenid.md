# VMGENID Design

## Summary

VMGENID is a mechanism that allows a hypervisor to notify a guest Linux kernel that it has been restored from a snapshot, so the kernel can immediately reseed its cryptographically secure random number generator (CSPRNG) and invalidate any secrets — such as WireGuard session keys — that would otherwise be duplicated across restored VM instances. This implementation adds a VMGENID device to libkrun for x86_64 and aarch64, without requiring any user-facing API.

The device works by allocating a fixed 4KB page in guest physical memory that holds a 128-bit GUID. On each snapshot restore, the VMM writes a fresh random GUID to that page and fires a platform interrupt — a GED (Generic Event Device) interrupt delivered via HW-reduced ACPI on x86_64, and a GIC SPI interrupt described via device tree on aarch64. The guest kernel's vmgenid driver detects the GUID change in its interrupt handler and calls `add_vmfork_randomness()`, which triggers the notifier chain. Because libkrun boots kernels directly without firmware, this design uses a fixed GUID page address rather than the firmware-negotiated address used by QEMU, and it introduces a minimal HW-reduced ACPI table stack (RSDP, XSDT, FADT, DSDT) that is new to libkrun but follows the same approach used by Cloud Hypervisor.

## Definition of Done

When a libkrun VM is restored from snapshot, the guest Linux kernel detects a VMGENID change and triggers `add_vmfork_randomness()`, causing immediate CSPRNG reseed, WireGuard key expiration, and any other vmfork notifier subscribers to fire.

**Success criteria:**
- x86_64: HW-reduced ACPI tables (RSDP, XSDT, FADT, DSDT) expose a VMGENID device via GED (Generic Event Device); GED interrupt fires on restore
- aarch64: Device tree node with `compatible = "microsoft,vmgenid"` exposes VMGENID; SPI interrupt fires on restore
- On each snapshot restore, hypervisor writes a new GUID to guest memory and triggers the appropriate interrupt
- The existing `test_snapshot_rng_reseed` integration test passes — two restores from the same snapshot produce different `/dev/urandom` output
- VMGENID is always present on x86_64 and aarch64 (no opt-in API)
- Unused `on_restore_complete()` hook and RNG device snapshot additions from the rng worktree are removed

**Out of scope:**
- macOS / HVF support
- RISC-V support
- User-facing API to set/query GUID
- Full ACPI table infrastructure beyond what VMGENID requires

## Acceptance Criteria

### vmgenid.AC1: GUID lifecycle
- **vmgenid.AC1.1 Success:** Fresh random 128-bit GUID is generated and written to guest page at offset 40 on VM creation
- **vmgenid.AC1.2 Success:** `update_guid()` produces a different GUID each invocation and writes it to the correct guest physical address

### vmgenid.AC2: x86_64 ACPI discovery
- **vmgenid.AC2.1 Success:** Kernel finds RSDP in EBDA scan range, parses XSDT → FADT, enters HW-reduced ACPI mode
- **vmgenid.AC2.2 Success:** vmgenid driver binds to `\_SB.VGEN` device via CID `"VMGENCTR"`
- **vmgenid.AC2.3 Success:** vmgenid driver evaluates ADDR method and reads initial GUID from guest memory

### vmgenid.AC3: aarch64 device tree discovery
- **vmgenid.AC3.1 Success:** FDT contains vmgenid node with `compatible = "microsoft,vmgenid"`, `reg`, and `interrupts` properties
- **vmgenid.AC3.2 Success:** vmgenid driver binds via device tree compatible match
- **vmgenid.AC3.3 Success:** vmgenid driver reads initial GUID from `reg` address and registers IRQ handler

### vmgenid.AC4: Snapshot restore triggers reseed
- **vmgenid.AC4.1 Success:** After restore, VMM writes a new GUID to the guest page before vCPUs resume
- **vmgenid.AC4.2 Success:** VMM injects the platform-specific interrupt (GED on x86_64, SPI on aarch64) after writing the GUID
- **vmgenid.AC4.3 Success:** Guest kernel logs `"crng reseeded due to virtual machine fork"` after restore
- **vmgenid.AC4.4 Success:** Two VMs restored from the same snapshot produce different 32-byte `/dev/urandom` output and different GUIDs

### vmgenid.AC5: ACPI infrastructure
- **vmgenid.AC5.1 Success:** x86_64 FADT has `HW_REDUCED_ACPI` flag set (bit 20) and revision 6
- **vmgenid.AC5.2 Failure:** GUID page address does not appear in E820 memory map entries

### vmgenid.AC6: Cleanup
- **vmgenid.AC6.1 Success:** `on_restore_complete()` method removed from `VirtioDevice` trait
- **vmgenid.AC6.2 Success:** No snapshot-specific additions remain in the Rng device that were added by the rng worktree

## Glossary

- **VMGENID**: A Microsoft-specified device that exposes a 128-bit VM Generation ID to the guest. The guest kernel uses it to detect snapshot restores and take defensive action (CSPRNG reseed, key expiration, etc.).
- **GUID**: Globally Unique Identifier — a 128-bit value used here as the generation ID written into the guest's GUID page. A new random GUID is written on every restore.
- **CSPRNG**: Cryptographically Secure Pseudo-Random Number Generator — the kernel's entropy pool that backs `/dev/urandom` and `/dev/random`. On snapshot restore, two VMs would share identical CSPRNG state unless explicitly reseeded.
- **`add_vmfork_randomness()`**: Linux kernel function that injects entropy and triggers the vmfork notifier chain; called by the vmgenid driver when it detects a GUID change.
- **HW-reduced ACPI**: An ACPI operating mode (FADT flag bit 20) that eliminates hardware register blocks (GPE, PM timer, SCI) and replaces them with software-only event delivery. Appropriate for virtual machines that have no real power management hardware.
- **RSDP**: Root System Description Pointer — the ACPI entry point, placed in the EBDA scan range (0xE0000–0xFFFFF) where the kernel searches for it at boot.
- **XSDT**: Extended System Description Table — the 64-bit ACPI root table that lists other top-level tables (here, just the FADT).
- **FADT**: Fixed ACPI Description Table — describes platform capabilities and points to the DSDT. This implementation uses revision 6 with the `HW_REDUCED_ACPI` flag.
- **DSDT**: Differentiated System Description Table — contains AML bytecode describing platform devices. Holds the `\_SB.VGEN` and `\_SB.GED` device definitions.
- **AML**: ACPI Machine Language — bytecode embedded in DSDT/SSDT tables. The `acpi_tables` crate generates AML directly in Rust.
- **GED**: Generic Event Device (`ACPI0013`) — used in HW-reduced ACPI to map a single interrupt to ACPI notifications. Its `_EVT` method dispatches `Notify` calls to other ACPI devices.
- **`_CID` / `_HID`**: ACPI device ID methods. `_HID` is the primary hardware ID; `_CID` is a compatible ID. The Linux vmgenid driver matches on `_CID = "VMGENCTR"`.
- **ADDR method**: ACPI method on the VMGENID device returning `[guid_page_addr + 40, 0]` — the physical address where the driver reads the GUID.
- **EBDA**: Extended BIOS Data Area — physical memory region (0xE0000–0xFFFFF) scanned by the kernel to locate the ACPI RSDP.
- **E820**: BIOS memory map interface (x86_64) describing which physical memory ranges are usable RAM vs reserved. The GUID page must be excluded.
- **FDT / Device Tree**: Flattened Device Tree — hardware description passed from hypervisor to kernel on aarch64. Analogous to ACPI on x86_64.
- **GIC / SPI**: GIC is the ARM Generic Interrupt Controller. SPI (Shared Peripheral Interrupt) is a GIC interrupt type for device interrupts.
- **`acpi_tables` crate**: A rust-vmm crate (used by Cloud Hypervisor and Firecracker) providing Rust types for ACPI table generation and AML bytecode.
- **`Snapshottable` trait**: A libkrun trait for device state serialization during snapshot/restore. `Vmgenid` intentionally does not implement this — its GUID is always regenerated fresh.
- **`MmioTransport`**: The libkrun virtio MMIO bus wrapper. VMGENID is a platform device and bypasses this path.
- **`VirtioDevice` trait**: The libkrun trait all virtio devices implement. The `on_restore_complete()` hook being removed was a workaround that VMGENID supersedes.
- **vmfork notifier chain**: A Linux kernel notification chain fired by `add_vmfork_randomness()`. Subscribers include the CSPRNG reseeder and WireGuard's key expiration logic.
- **Microsoft spec R1d**: Requirement that the GUID page must not appear in the guest's memory map as usable RAM.
- **OVMF SDT Header Probe Suppressor**: Convention where the GUID sits at offset 40 within its page, after a header area. The Linux vmgenid driver's ADDR method accounts for this offset.

## Architecture

VMGENID exposes a VM Generation ID to the guest kernel so it can detect snapshot restores and reseed its CSPRNG. The implementation has three layers: a shared device model, platform-specific discovery (ACPI on x86_64, device tree on aarch64), and snapshot-restore integration.

### Shared Device Model

A `Vmgenid` struct in `src/devices/src/vmgenid/` owns a 128-bit GUID and the guest physical address of a fixed 4KB GUID page. On construction it generates a random GUID and writes it to the guest page. It provides `update_guid(mem: &GuestMemoryMmap)` which generates a new random GUID, writes it to the page, and returns the old/new values for logging. The GUID is stored at offset 40 within the page (matching the OVMF SDT Header Probe Suppressor convention used by QEMU, which the Linux vmgenid driver's ACPI ADDR method accounts for).

The GUID page is at a fixed guest physical address per architecture (outside E820/memory map entries, per Microsoft spec requirement R1d). The Vmgenid struct does NOT implement `Snapshottable` — its state is not persisted in snapshots. A fresh GUID is written on every restore.

### x86_64: HW-Reduced ACPI with GED

libkrun currently has no ACPI table infrastructure. This design adds minimal HW-reduced ACPI support using the `acpi_tables` crate (from rust-vmm, used by Cloud Hypervisor and Firecracker).

**Tables generated at boot** in `src/arch/src/x86_64/acpi.rs`:

| Table | Purpose |
|-------|---------|
| RSDP | Entry point placed in EBDA scan range (0xE0000–0xFFFFF). Points to XSDT. |
| XSDT | Lists FADT as sole entry. |
| FADT | Revision 6 with `HW_REDUCED_ACPI` flag (bit 20). Points to DSDT. No GPE blocks, no PM register blocks. |
| DSDT | Contains AML for `\_SB.VGEN` (VMGENID device) and `\_SB.GED` (Generic Event Device). |

**DSDT AML devices:**

`\_SB.VGEN` — VMGENID device:
- `_HID` = vendor-specific identifier (driver matches on `_CID`)
- `_CID` = `"VMGENCTR"` (matches Linux vmgenid driver's `acpi_device_id` table)
- `_STA` returns 0x0F
- `ADDR` method returns a two-element package: `[guid_page_addr + 40, 0]`

`\_SB.GED` — Generic Event Device (ACPI HID `"ACPI0013"`):
- `_CRS` declares a single edge-triggered interrupt (allocated IRQ)
- `_EVT` method calls `Notify(\_SB.VGEN, 0x80)` (Status Change)

HW-reduced ACPI eliminates the need for GPE register emulation and SCI routing. The GED maps a single interrupt directly to the VMGENID notification — no I/O port trapping, no status/enable register state machine. Cloud Hypervisor uses the same HW-reduced ACPI + GED pattern for event delivery.

**Memory layout**: Tables placed contiguously starting at a reserved address below 4GB (in the EBDA/ROM scan region). The GUID page is a separate 4KB allocation outside E820 RAM entries.

### aarch64: Device Tree

libkrun already generates FDT via `FdtWriter` in `src/devices/src/fdt/aarch64.rs`. A new node is added:

```
vmgenid@{addr} {
    compatible = "microsoft,vmgenid";
    reg = <{guid_page_addr} 0x1000>;
    interrupts = <GIC_SPI {irq} IRQ_TYPE_EDGE_RISING>;
};
```

The Linux vmgenid driver matches on `compatible = "microsoft,vmgenid"`, reads `reg` to find the GUID, and requests the IRQ. On restore, the VMM injects the SPI interrupt via KVM GIC and the driver's IRQ handler calls `add_vmfork_randomness()`.

### Snapshot/Restore Integration

The restore sequence in `src/vmm/src/lib.rs` gains a new step after devices are restored and re-activated:

1. All devices restored and re-activated (existing flow)
2. **New**: `vmgenid.update_guid(mem)` writes a fresh random GUID to the fixed guest page
3. **New**: Platform-specific interrupt injection (GED IRQ on x86_64, SPI on aarch64)
4. vCPUs resume (existing flow)

On first boot, the GUID is written during VM construction. No interrupt fires — the vmgenid driver reads the initial GUID during probe and stores it. Notifications only fire on restore when the GUID changes.

### Data Flow

```
First boot:
  VMM generates GUID → writes to guest page → kernel vmgenid driver probes, stores initial GUID

Snapshot save:
  Guest page (with GUID) captured in memory dump → Vmgenid struct state NOT serialized

Snapshot restore:
  Memory restored (old GUID in page) → devices re-activated →
  VMM writes NEW GUID to page → injects interrupt →
  vmgenid driver handler fires → compares old vs new → different →
  add_vmfork_randomness() → crng_reseed() + WireGuard key expiration + notifier chain
```

## Existing Patterns

**ACPI on x86_64**: libkrun currently uses MP Table (`src/arch/src/x86_64/mptable.rs`) for CPU/IOAPIC enumeration, written as a binary struct to guest memory at 0x9FC00. ACPI tables follow the same pattern — binary data written to guest memory at known addresses. The `acpi_tables` crate handles struct layout and checksum calculation.

**Device tree on aarch64**: Existing FDT generation in `src/devices/src/fdt/aarch64.rs` uses `FdtWriter` with `begin_node()`, `property_string()`, `property()`, `property_array_u32()` API. The vmgenid node follows the same pattern as existing GPIO, RTC, and serial nodes. The `create_devices_node()` function dispatches on `DeviceType` — a new `Vmgenid` variant routes to a `create_vmgenid_node()` function.

**Interrupt injection on aarch64**: Existing virtio devices use `register_irqfd` to bind EventFds to GIC IRQs. The vmgenid SPI interrupt follows the same allocation and injection path.

**Legacy devices on x86_64**: Port-based devices (CMOS, i8042, serial) are registered with `PortIODeviceManager` and implement `Snapshottable`. The GED on x86_64 does not need PortIO — it's an interrupt-only device with no registers. The interrupt is injected via KVM irqchip, same as existing devices.

**Snapshot restore hooks**: `MmioTransport::complete_restore()` handles virtio device re-activation. The vmgenid GUID update and interrupt injection happen at the VMM level after all devices are restored, not through the MmioTransport path — vmgenid is a platform device, not a virtio device.

**Divergence from QEMU**: QEMU uses traditional ACPI with GPE register emulation and fw_cfg for GUID address sharing. This design uses HW-reduced ACPI (matching Cloud Hypervisor) and a fixed GUID address (since libkrun boots the kernel directly without firmware). The Linux vmgenid driver works with both approaches.

## Additional Considerations

**Kernel configuration**: The guest kernel must have `CONFIG_ACPI=y` (x86_64) or `CONFIG_OF=y` (aarch64) and `CONFIG_VMGENID=y` or `=m`. Stock distribution kernels (Ubuntu, Fedora) include these. If libkrun's test kernel is custom-built, these configs must be enabled.

**GUID page E820 exclusion**: The GUID page must not appear in E820 (x86_64) or `/memory` FDT nodes (aarch64) as usable RAM. The kernel must not allocate it for general use. This is enforced by placing the page in a reserved region outside the RAM entries reported to the kernel.

**HW-reduced ACPI scope**: This design adds the minimum ACPI infrastructure for VMGENID. The FADT and DSDT can be extended later for other platform features (power management, device hotplug) without architectural changes. The `acpi_tables` crate supports the full ACPI table set.
