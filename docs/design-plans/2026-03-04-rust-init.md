# Rust Init Migration Design

## Summary

This design migrates the guest init process from a C binary (`init/init.c`) to a Rust static binary compiled against musl libc. The init process is PID 1 inside every libkrun virtual machine: it mounts filesystems, configures the network loopback interface, applies resource limits, redirects stdio, and finally exec's the user-specified workload — making it a critical piece of the boot path.

The migration has two interlocking parts. On the host side, the VM builder gains logic to compute the `/dev/vport{X}p{Y}` device paths for any virtio-console ports wired to the guest's stdin, stdout, and stderr, and injects those paths into the kernel command line as `KRUN_STDIN_DEV`, `KRUN_STDOUT_DEV`, and `KRUN_STDERR_DEV` environment variables. On the guest side, the Rust init reads these variables directly from its process environment and opens the device nodes, replacing the current sysfs directory scan that walks `/sys/class/virtio-ports/` at runtime. All other configuration (workload path, working directory, resource limits, hostname) continues to arrive via the existing `KRUN_*` kernel cmdline convention. The migration is structured as four sequential phases so that the VM remains bootable after each phase, and confidential-computing branches (SEV/SNP/TDX/LUKS) are explicitly deferred to future work.

## Definition of Done

1. A Rust static musl binary replaces `init/init.c` for the common (non-SEV/non-TDX) boot path
2. No config file — all config via kernel cmdline env vars only
3. Host adds `KRUN_STDIN_DEV`, `KRUN_STDOUT_DEV`, `KRUN_STDERR_DEV` to cmdline when non-terminal virtio-console ports are configured
4. Guest init opens port paths directly from env vars — no sysfs scanning of `/sys/class/virtio-ports/`
5. Sequential execution (Option A from brainstorming) — simpler code, no thread overhead; parallelism deferred to future work if profiling warrants it
6. All existing external contracts preserved: kernel cmdline `init=/init.krun` entry, virtiofs ioctls for exit code and root-dir removal, fork-and-wait pid1 semantics
7. SEV/SNP/TDX/LUKS branches left as future work (not in scope)

## Acceptance Criteria

### rust-init.AC1: Rust init binary builds and boots
- **rust-init.AC1.1 Success:** `just build-init` produces a static musl binary at `init/init`
- **rust-init.AC1.2 Success:** Binary is statically linked with no dynamic library dependencies
- **rust-init.AC1.3 Success:** VM boots with Rust init and successfully execs a workload (e.g. `/bin/sh`)
- **rust-init.AC1.4 Failure:** Init prints error and exits non-zero if mount_filesystems() fails

### rust-init.AC2: Host injects port device paths into cmdline
- **rust-init.AC2.1 Success:** When non-terminal stdin port is configured, `KRUN_STDIN_DEV=/dev/vportXpY` appears on guest kernel cmdline
- **rust-init.AC2.2 Success:** Same for `KRUN_STDOUT_DEV` and `KRUN_STDERR_DEV`
- **rust-init.AC2.3 Edge:** When port is a terminal (not a pipe), the corresponding `KRUN_*_DEV` env var is absent from cmdline
- **rust-init.AC2.4 Edge:** When no console ports are configured, all three env vars are absent

### rust-init.AC3: Guest stdio redirect from env vars
- **rust-init.AC3.1 Success:** Guest stdin reads from the device specified by `KRUN_STDIN_DEV`
- **rust-init.AC3.2 Success:** Guest stdout writes to the device specified by `KRUN_STDOUT_DEV`
- **rust-init.AC3.3 Success:** Guest stderr writes to the device specified by `KRUN_STDERR_DEV`
- **rust-init.AC3.4 Edge:** When `KRUN_STDIN_DEV` is absent, stdin is not redirected (uses kernel default)
- **rust-init.AC3.5 Failure:** When `KRUN_STDIN_DEV` contains a non-existent path, init prints error but continues (doesn't abort boot)

### rust-init.AC4: Env var config works correctly
- **rust-init.AC4.1 Success:** `KRUN_INIT` sets the exec path for the workload
- **rust-init.AC4.2 Success:** `KRUN_WORKDIR` sets the working directory before exec
- **rust-init.AC4.3 Success:** `KRUN_RLIMITS` sets resource limits (id,cur,max triples)
- **rust-init.AC4.4 Success:** `HOSTNAME` sets the guest hostname
- **rust-init.AC4.5 Success:** `KRUN_HOME` / `KRUN_TERM` set HOME / TERM env vars
- **rust-init.AC4.6 Edge:** Missing optional env vars (KRUN_WORKDIR, KRUN_RLIMITS, etc.) are handled gracefully

### rust-init.AC5: Exit code and lifecycle contracts preserved
- **rust-init.AC5.1 Success:** Workload exit code is reported to host via virtiofs KRUN_EXIT_CODE_IOCTL
- **rust-init.AC5.2 Success:** When KRUN_INIT_PID1=1, init execs workload directly (no fork)
- **rust-init.AC5.3 Success:** When KRUN_INIT_PID1 is unset, init forks child, waits for it, reports exit code
- **rust-init.AC5.4 Success:** Signal-killed workloads report exit code = signal + 128
- **rust-init.AC5.5 Success:** stdout/stderr are drained (tcdrain) before init exits
- **rust-init.AC5.6 Success:** Block root device pivot (KRUN_BLOCK_ROOT_DEVICE) works with chroot + re-mount

### rust-init.AC6: C init removed, build system updated
- **rust-init.AC6.1 Success:** `init/init.c` and `init/jsmn.h` are deleted
- **rust-init.AC6.2 Success:** `just all` passes with Rust init
- **rust-init.AC6.3 Success:** `just integration` passes with Rust init

## Glossary

- **PID 1 / init process**: The first process started by the Linux kernel after boot. Must reap all orphaned child processes; if it exits, the kernel panics.
- **musl**: A lightweight C standard library designed for static linking. Rust binaries targeting `x86_64-unknown-linux-musl` produce self-contained executables with no dynamic library dependencies.
- **virtio-console**: A paravirtualized character device exposed to the guest as `/dev/hvcN` (console) or `/dev/vport{X}p{Y}` (named ports). libkrun uses named ports to pass the host's stdin/stdout/stderr into the guest.
- **`/dev/vport{X}p{Y}`**: Device node path for a virtio-console port. `X` is the virtio device index, `Y` is the port index within that device.
- **sysfs (`/sys/class/virtio-ports/`)**: Linux kernel virtual filesystem exposing device metadata. The current C init scans this to discover which `/dev/vport*` path corresponds to each named port — a runtime lookup this design eliminates.
- **kernel cmdline**: A string passed from the hypervisor to the Linux kernel at boot. `KEY=VALUE` tokens become environment variables of the init process, making it the host-to-guest configuration channel in libkrun.
- **`KRUN_*` env vars**: libkrun's convention for host→guest config. Existing: `KRUN_INIT` (workload path), `KRUN_WORKDIR`, `KRUN_RLIMITS`. This design adds `KRUN_STDIN_DEV`, `KRUN_STDOUT_DEV`, `KRUN_STDERR_DEV`.
- **virtiofs**: A virtio device that exposes a host directory to the guest as a filesystem. Also used for the `KRUN_EXIT_CODE_IOCTL` side channel.
- **`KRUN_EXIT_CODE_IOCTL`**: Custom ioctl issued by guest init against virtiofs to report the workload's exit status to the host.
- **`ConsolePortInfo`**: Struct in `builder.rs` recording the guest-visible device path for each virtio-console port. This design feeds it back into `ContextConfig` for cmdline injection.
- **`ContextConfig`**: Host-side configuration object accumulating all VM settings before `Builder::build()`.
- **fork-and-exec**: Init runs the workload as a child process (fork), waits for it (waitpid), collects exit code. When `KRUN_INIT_PID1=1`, init exec's directly (no fork).
- **`tcdrain`**: POSIX call that blocks until queued output is transmitted. Called before init exits to ensure the workload's output reaches the host.
- **SEV/SNP/TDX**: AMD/Intel confidential-computing technologies requiring additional init setup (attestation, encrypted disks). Out of scope for this migration.
- **LUKS**: Disk encryption standard. C init has a branch to unlock encrypted root devices via attestation. Out of scope.
- **`include_bytes!`**: Rust macro embedding a file's bytes into the compiled binary. `passthrough.rs` uses it to embed `init/init` into the libkrun library.
- **separate Cargo workspace**: Independent `Cargo.toml` with `[workspace]` (like `tests/`). Init uses its own workspace so musl build config doesn't affect the root workspace.

## Architecture

Rust static musl binary replaces `init/init.c`. All guest configuration arrives via kernel cmdline environment variables — no config files, no JSON parsing. The host-side `Builder` computes virtio-console port device paths at VM build time and injects them as `KRUN_STDIN_DEV`, `KRUN_STDOUT_DEV`, `KRUN_STDERR_DEV` into the kernel cmdline. The guest init reads these from its process environment and opens the devices directly, eliminating the current sysfs scan of `/sys/class/virtio-ports/`.

The init binary is a single Rust crate in `init/` compiled to `x86_64-unknown-linux-musl`. The output binary at `init/init` is picked up by the existing `include_bytes!` in `src/devices/src/virtio/fs/linux/passthrough.rs:38` — no changes to the embedding mechanism.

### Components

**Guest init binary** (`init/`):
- `init/Cargo.toml` — separate workspace (not part of root Cargo workspace), `x86_64-unknown-linux-musl` target
- `init/src/main.rs` — entry point, sequential boot flow, fork+exec

Dependencies: `libc` only. No async runtime, no serde, no allocator override.

**Host cmdline injection** (`src/libkrun/src/lib.rs`):
- `ContextConfig` gains three `Option<String>` fields: `stdin_dev`, `stdout_dev`, `stderr_dev`
- New `get_stdio_devs()` method returns cmdline strings like `KRUN_STDIN_DEV=/dev/vport3p1`
- Kernel cmdline assembly (line ~1004) includes `get_stdio_devs()` output

**Host port path computation** (`src/vmm/src/builder.rs`):
- After console port registration (line ~2891), the `ConsolePortInfo.device_path` for each named port (`krun-stdin`, `krun-stdout`, `krun-stderr`) is stored back into `ContextConfig`
- Device path formula: `/dev/vport{device_idx}p{port_idx}` (already computed at line ~2904)

### Data Flow

```
Host Builder::build()
  → create console ports with names ("krun-stdin", etc.)
  → compute device_path for each: /dev/vport{X}p{Y}
  → store paths in ContextConfig.stdin_dev / stdout_dev / stderr_dev
  → build kernel cmdline (includes KRUN_STDIN_DEV=... etc.)
  → configure_system() writes cmdline to guest memory

Guest kernel boots
  → passes cmdline env vars to init process environment

Guest init (PID 1)
  → reads KRUN_STDIN_DEV from env → open("/dev/vport3p1") → dup2(fd, 0)
  → reads KRUN_STDOUT_DEV from env → open("/dev/vport3p2") → dup2(fd, 1)
  → reads KRUN_STDERR_DEV from env → open("/dev/vport3p3") → dup2(fd, 2)
  → no sysfs interaction
```

## Existing Patterns

**Separate workspace for guest binaries**: `tests/` has its own `Cargo.lock` and workspace separate from the root. The Rust init follows the same pattern — `init/` is an independent Cargo workspace with its own `Cargo.lock`. This avoids contaminating the root workspace with musl-specific build config.

**Init binary embedding**: `include_bytes!("../../../../../../init/init")` in `passthrough.rs:38` picks up whatever binary exists at `init/init`. The Rust rewrite produces a binary at the same path — no changes to the embedding mechanism.

**Kernel cmdline env vars**: The existing pattern for host→guest config is `KRUN_*` env vars on the kernel cmdline (`KRUN_INIT`, `KRUN_WORKDIR`, `KRUN_RLIMITS`, etc.). The new `KRUN_STDIN_DEV` / `KRUN_STDOUT_DEV` / `KRUN_STDERR_DEV` follow this convention exactly.

**ConsolePortInfo**: Already computed in `builder.rs:2891-2907` with `device_path` field. Currently returned to the caller via `VmDeviceInfo` but not used for cmdline injection. This design adds a feedback path from port registration back to `ContextConfig`.

**Goal:** Establish the Rust init crate, build system integration, and a minimal binary that boots successfully (mounts filesystems, execs `/bin/sh`).

**Goal:** Rust init reads port device paths from env vars and redirects stdin/stdout/stderr without sysfs scanning.

**Dependencies:** Phase 2 (host must inject the env vars)

## Additional Considerations

**SEV/SNP/TDX migration path:** The C init remains available in git history. Future work can port the `#ifdef SEV` / `#ifdef TDX` branches to Rust with `#[cfg(feature = "sev")]` / `#[cfg(feature = "tdx")]` gating. The LUKS passphrase flow (cryptsetup fork, securityfs mount) and TDX block device chroot are self-contained and can be added as separate features.

**Binary size:** With only `libc` as a dependency and musl static linking, the Rust binary should be comparable to the C binary (~50-100KB stripped). If it grows significantly, `#[no_std]` with a minimal allocator is possible but unlikely to be needed.

**KRUN_RLIMITS format:** The existing format (`id,cur,max` triples space-separated) is preserved as-is. No protocol change for any existing env var — only three new ones added.
