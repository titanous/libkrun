# VM Exit Handling Design

## Summary

libkrun is an embeddable library that runs lightweight virtual machines via KVM (Linux) or HVF (macOS). Today, when a guest VM exits — whether by halting, requesting a reboot, or encountering a fatal error — the library calls `libc::_exit()` and terminates the host process entirely. This makes libkrun unsuitable for use in long-lived host processes that need to run multiple VMs sequentially, inspect the exit reason, or clean up resources after a VM has finished.

This design replaces the `_exit()` call with a structured return value. `Context::run()`, the blocking entry point that drives the VM event loop, will return `Result<VmExit, StartError>` where `VmExit` is an enum encoding the reason the VM stopped: clean shutdown (with exit code), reboot request, or fatal error. The approach threads a shared `Arc<Mutex<Option<VmExit>>>` between the VMM event loop and the `Context` owner so the event loop can signal exit reason without process termination. A companion fix unblocks Linux vCPU threads that currently wait on a `Barrier` forever (relying on `_exit()` to kill them), replacing the barrier with a shared exit flag so threads can be joined cleanly. The change is implemented in four phases: introducing the `VmExit` type and shared state, fixing vCPU thread cleanup, updating `Context::run()` to return the value, and adding an integration test that verifies both the exit reason and the absence of resource leaks.

## Definition of Done
- `Context::run()` returns `Result<VmExit, StartError>` instead of calling `libc::_exit()`
- `VmExit` is a structured enum with distinct variants for: normal shutdown (with exit code), reboot requested, and errors (triple fault, internal error, etc.)
- Internal device cleanup (`VmmExitObserver`) still runs before returning
- An integration test exercises the exit path: guest exits, host receives the exit reason and can act on it

## Acceptance Criteria

### vm-exit.AC1: Context::run() returns Result<VmExit, StartError>
- **vm-exit.AC1.1 Success:** Normal guest shutdown (HLT) returns `VmExit::Shutdown { exit_code: 0 }`
- **vm-exit.AC1.2 Success:** Guest-set exit code (via virtio-fs ioctl) is returned in `VmExit::Shutdown { exit_code }`
- **vm-exit.AC1.3 Success:** KVM_SYSTEM_EVENT_RESET returns `VmExit::RebootRequested`
- **vm-exit.AC1.4 Success:** Caller regains control after `run()` returns (process does not terminate)

### vm-exit.AC2: VmExit enum has correct variants
- **vm-exit.AC2.1 Success:** `VmExit::Error { message }` is returned for vCPU fatal errors (FailEntry, InternalError)
- **vm-exit.AC2.2 Success:** `StartError` is returned for pre-run failures (build errors, vCPU spawn failures) — distinct from runtime `VmExit::Error`

### vm-exit.AC3: Internal cleanup runs before returning
- **vm-exit.AC3.1 Success:** All registered `VmmExitObserver` callbacks fire before `run()` returns
- **vm-exit.AC3.2 Success:** vCPU threads are joined before `run()` returns (no dangling threads)

### vm-exit.AC4: Resource cleanup verified by integration test
- **vm-exit.AC4.1 Success:** Thread count (`/proc/self/task`) returns to pre-VM baseline after `run()` returns and context is dropped
- **vm-exit.AC4.2 Success:** File descriptor count (`/proc/self/fd`) returns to baseline (±2 tolerance)
- **vm-exit.AC4.3 Success:** Memory map count (`/proc/self/maps`) returns to baseline (±2 tolerance)

## Glossary

- **vCPU**: Virtual CPU — a thread managed by the hypervisor (KVM/HVF) that executes guest machine instructions. Each VM may have one or more vCPU threads.
- **KVM**: Kernel-based Virtual Machine — Linux kernel subsystem that exposes an `ioctl`-based API for running hardware-accelerated virtual machines.
- **HVF**: Hypervisor Framework — the macOS equivalent of KVM; provides hardware-accelerated VM execution on Apple silicon and Intel Macs.
- **VMM**: Virtual Machine Monitor — the user-space component (`vmm` crate) that configures VM memory, devices, and vCPU state and services KVM/HVF exit events.
- **HLT**: x86 `HLT` instruction — executed by the guest to signal it has no more work; KVM surfaces this as `KVM_EXIT_HLT`, which libkrun treats as a clean shutdown.
- **KVM_SYSTEM_EVENT_RESET**: A KVM exit reason indicating the guest has requested a reboot. Distinct from shutdown.
- **FailEntry / InternalError**: KVM exit codes (`KVM_EXIT_FAIL_ENTRY`, `KVM_EXIT_INTERNAL_ERROR`) indicating a fatal hypervisor-level error.
- **EventManager**: `polly::event_manager::EventManager` — an `epoll`-based reactor that dispatches I/O readiness events to registered device handlers. `Context::run()` spins on this loop.
- **EventFd (`exit_evt`)**: A Linux file descriptor used as a one-shot signal; the vCPU thread writes to `exit_evt` when it detects VM exit, waking the EventManager.
- **`VmmExitObserver`**: A trait in `src/devices/src/virtio/device.rs` that virtio devices implement to receive a cleanup callback (`on_vmm_exit`) before the VMM finishes shutting down.
- **`Barrier`**: Rust standard-library synchronization primitive; currently used in the Linux vCPU `exited()` state to stall threads indefinitely (a workaround for the lack of a real exit signal).
- **`StartError`**: Existing error type for failures before or during VM startup — distinct from `VmExit::Error` which represents runtime failures.
- **virtio-fs ioctl**: Mechanism by which the guest writes an exit code into a virtio-fs device; that value takes precedence over the vCPU-reported exit code.
- **`#[host]` / `#[guest]` proc macros**: Procedural macros in the `tests/` workspace that split a test into host-side and guest-side binaries coordinated over vsock.

## Architecture

Shared exit state approach: an `Arc<Mutex<Option<VmExit>>>` is shared between `Vmm` (inside the event loop) and `Context` (owns the loop). When the VM exits, `Vmm::process()` constructs a `VmExit` value and stores it in the shared state instead of calling `libc::_exit()`. `Context::run()` checks the shared state after each `event_manager.run()` iteration and returns when a `VmExit` is present.

### VmExit Enum

```rust
/// Reason the VM exited.
pub enum VmExit {
    /// Guest initiated a clean shutdown (HLT or ACPI shutdown).
    /// Contains the exit code set by the guest (0 = success).
    Shutdown { exit_code: i32 },

    /// Guest requested a reboot (KVM_SYSTEM_EVENT_RESET).
    RebootRequested,

    /// vCPU encountered a fatal error (triple fault, internal KVM error).
    Error { message: String },
}
```

Exit code uses `i32` to match the existing `Arc<AtomicI32>` convention. Guest-set exit code (via virtio-fs ioctl) takes precedence over vCPU-reported code, preserving the existing priority logic in `Vmm::process()`.

`StartError` remains for errors that prevent the VM from starting. `VmExit::Error` covers errors during VM execution.

### Data Flow

1. vCPU thread detects exit (HLT, Shutdown, SystemEvent, or error) in `src/vmm/src/linux/vstate.rs`
2. vCPU sends `VcpuResponse::Exited(exit_code)` via channel, writes to `exit_evt` EventFd
3. EventManager dispatches `exit_evt` to `Vmm::process()` in `src/vmm/src/lib.rs`
4. `Vmm::process()` resolves exit code (guest-set > vCPU > default 0), determines `VmExit` variant
5. `Vmm::process()` runs exit observers, stores `VmExit` in shared state, returns normally
6. `Context::run()` sees `VmExit`, joins vCPU threads, returns `Ok(VmExit)` to caller

### Signal Handlers

Signal handlers for SIGSYS, SIGBUS, and SIGSEGV in `src/vmm/src/signal_handler.rs` continue to call `libc::_exit()` directly. These signals indicate host-process corruption where returning is unsafe.

## Existing Patterns

The shared-state approach follows the existing `exit_code: Arc<AtomicI32>` pattern already used in `Vmm` to share the guest-set exit code between virtio-fs device threads and the VMM event loop (`src/vmm/src/lib.rs:212`).

The `VmmExitObserver` trait in `src/devices/src/virtio/device.rs:258-267` provides the existing device cleanup mechanism. This design preserves it — observers are notified before `VmExit` is stored, exactly as before.

The integration test follows the established `#[host]`/`#[guest]` proc macro pattern from `tests/test_cases/src/test_rust_api.rs`, using `setup_fs_builder()` from `tests/test_cases/src/krun_rust.rs`.

**Divergence from existing patterns:** On Linux, vCPU threads currently block forever on `Barrier::new(2)` in the `exited()` state (`src/vmm/src/linux/vstate.rs:1817-1824`), relying on `_exit()` to kill them. This design replaces the barrier with a shared exit flag so threads can unwind and be joined. macOS vCPU threads already exit naturally (break from run loop in `src/vmm/src/macos/vstate.rs:539-541`).

**Components:**

- `Vmm::stop()` — sets the exit flag before storing `VmExit` so vCPU threads can unwind
- macOS path in `src/vmm/src/macos/vstate.rs` — already exits naturally, verify no changes needed

**Dependencies:** Phase 1 (shared exit state exists)

**Done when:** vCPU threads terminate after VM exit on both Linux and macOS. Covers vm-exit.AC3.1, vm-exit.AC3.2.

## Additional Considerations

**Reboot handling by caller:** When `Context::run()` returns `VmExit::RebootRequested`, the caller can rebuild and restart the VM. The current design does not provide a "restart in place" API — the caller must create a new `Builder` and `Context`. This keeps the API simple and avoids complex state reset logic.

**Existing tests:** Tests that currently call `context.run()` via `thread::spawn` and join the thread will continue to work. The thread will now join normally (returning `Result<VmExit, StartError>`) instead of being killed by `_exit()`. Tests that don't examine the return value are unaffected.
